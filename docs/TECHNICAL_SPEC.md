# CineBase — техническое задание по фазам

Версия 1 • 25 октября 2026 года • Статус: план реализации.

## 1. Цель и границы проекта

Создать самостоятельное веб-приложение для поиска и изучения фильмов с быстрым, понятным и приятным UX. Пользователь открывает каталог без регистрации, находит фильм, получает полезную информацию и продолжает исследование через людей, жанры и подборки.

«Библиотека всех фильмов» означает расширяемый каталог с внешним источником данных. Первая версия честно показывает имеющееся покрытие. Тестовая выборка из нескольких десятков фильмов не выдаётся за полную мировую базу.

**Включено:** Home/Discover, каталог, поиск, фильтры, сортировки, страницы фильмов, фильмографии, редакционные подборки, доступный адаптивный интерфейс и versioned API для будущего мобильного клиента.

**Следующие проекты:** пользовательские аккаунты, дневник, личные оценки, watchlist с синхронизацией, комментарии, чаты, подписки и социальная лента относятся к Cinephily Base и объединению продукта. Персональные ML-рекомендации относятся к отдельным экспериментам. Их отсутствие не блокирует CineBase.

Полный production deploy, домен, почта и CI/CD остаются на позднем этапе общего плана. В этом проекте нужны воспроизводимый локальный запуск, проверки и сборка, готовая к дальнейшему размещению.

## 2. Пользовательские сценарии

| ID | Сценарий | Проверяемый результат |
| --- | --- | --- |

| U2 | Найти фильм по названию, альтернативному названию или названию с годом | Релевантный результат; ремейки различаются годом и режиссёром |
| U3 | Подобрать фильм через жанр, десятилетие и длительность | Фильтры комбинируются и сохраняются в URL |
| U4 | Открыть фильм и вернуться к результатам | Сохраняются запрос, фильтры, загруженные карточки и позиция прокрутки |
| U5 | Перейти от фильма к режиссёру или актёру | Открывается фильмография с обратным переходом |

## 3. Архитектура и рабочий стек

Один репозиторий, один backend и одна PostgreSQL. UI получает данные через публичный API. Секреты поставщика остаются на backend.

| Часть | Выбор | Назначение |
| --- | --- | --- |
| Web | React + TypeScript + Next.js App Router | Публичные страницы, маршруты, server rendering и интерактивный UI |
| API | Python + FastAPI + Pydantic | Контракты и обработка запросов каталога |
| Persistence | SQLAlchemy + Alembic + PostgreSQL | Единая схема и миграции |
| Поиск | Нормализованные названия + PostgreSQL `pg_trgm` | Точное совпадение, префиксы и опечатки |
| Каталог | FixtureProvider + внешний provider adapter | Локальная разработка без внешней сети и импорт реальных данных |
| Тесты | pytest + PostgreSQL integration; web E2E | Корректность данных и основных сценариев |

Это рабочий выбор для данного ТЗ. Поддерживаемые версии и lockfiles фиксируются в фазе 2 после проверки совместимости. Redis, отдельная очередь и поисковый кластер добавляются только при измеренной необходимости; начальный импорт выполняется управляемой CLI-командой.

```text
cinebase/
  apps/
    web/                 # Next.js
    api/                 # FastAPI, migrations, integration tests
  packages/
    api-client/          # TypeScript client generated from OpenAPI
  fixtures/              # deterministic catalog and local sample art
  docs/
    TECHNICAL_SPEC.md
    LEGACY_AUDIT.md
    verification/        # measured results and scenario evidence
  compose.yaml           # local dependencies, added in phase 2
  README.md
```

UI-прототип использует DTO той же формы, что и API. Компоненты получают данные через один адаптер: переключение fixtures/API не требует переписывать экраны.

## 4. Модель данных

| Сущность | Минимальные поля и ограничения |
| --- | --- |
| Movie | UUID, canonical_title, original_title nullable, release_date nullable, release_year nullable, runtime_minutes nullable, synopsis nullable, original_language nullable, status, timestamps |
| ExternalId | movie_id, provider, external_id; UNIQUE(provider, external_id) |
| AlternateTitle | movie_id, title, normalized_title, locale nullable, source |
| Genre / MovieGenre | Справочник и связь с фильмом |
| Person / Credit | UUID человека, имя, внешний ID; movie_id/person_id/department/job/character/order |
| MovieAsset | movie_id, poster/backdrop, URL или local path, source, attribution, preferred |
| ProviderSnapshot | movie_id, provider, fetched_at, payload, source/version metadata |
| Collection / CollectionItem | slug UNIQUE, title, description, упорядоченные movie_id; UNIQUE(collection_id, movie_id) |

Инварианты:

- Внешний ID хранится отдельно от собственного UUID; повторный импорт одного внешнего фильма сохраняет UUID.
- Схожее название и год сами по себе не являются достаточным основанием склеивать фильмы разных поставщиков.
- Неизвестная длительность, дата, рейтинг или изображение представлены `null`, а не выдуманным значением.
- Фестивальная дата, региональная дата и год не подменяются временем импорта; неизвестный день не превращается в 1 января.
- Объявленные будущие релизы допустимы; ограничение `year <= 2030` не используется.
- Если показывается рейтинг поставщика, рядом указаны источник, шкала и число голосов при наличии. Он отличается от персональной оценки пользователя.
- Постеры и описания поступают из разрешённых источников; fixtures содержат локальные/synthetic assets и не требуют внешних запросов.

## 5. Контракт API

Общий prefix: `/api/v1`. Публичные методы доступны без аккаунта. Обслуживающие операции импорта выполняются через локальную CLI; общедоступных write/admin/cache-clear endpoints в первой версии нет.

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| GET | `/health/live` | Процесс отвечает; без зависимости от поставщика |
| GET | `/health/ready` | Собственная БД готова; недоступность поставщика не ломает локальный каталог |
| GET | `/api/v1/discover` | Редакционные блоки главной с понятными источниками |
| GET | `/api/v1/movies` | Поиск/каталог, фильтры, сортировка, страницы |
| GET | `/api/v1/movies/{id}` | Детальная карточка |
| GET | `/api/v1/movies/{id}/credits` | Актёры и команда |
| GET | `/api/v1/people/{id}` | Данные человека |
| GET | `/api/v1/people/{id}/movies` | Фильмография с ролью и пагинацией |
| GET | `/api/v1/genres` | Справочник для фильтров |
| GET | `/api/v1/collections` | Доступные подборки |
| GET | `/api/v1/collections/{slug}` | Описание подборки |
| GET | `/api/v1/collections/{slug}/movies` | Её упорядоченные фильмы |

Параметры `/movies`:

- `q`: строка после trim, до 200 символов; пустая означает browse.
- `genre`: повторяемый slug; между выбранными жанрами OR, между группами фильтров AND.
- `year_from`, `year_to`: включительные границы; некорректный диапазон даёт 422.
- `runtime_max`: положительное число минут; фильмы с неизвестной длительностью не подходят под этот фильтр.
- `sort`: `relevance`, `title_asc`, `release_desc`, `runtime_asc`; `relevance` требует непустой запрос.
- `limit`: default 24, диапазон 1–48; `cursor`: opaque continuation token.

Каждая сортировка имеет UUID tie-breaker и явное положение `null`. Cursor связан с сортировкой и фильтрами; при смене запроса/фильтров UI сбрасывает cursor. В курсоре поиска сохраняется полный ключ ранжирования; результаты стабильны в пределах фиксированной версии каталога. Изменение версии может потребовать начать выдачу заново.

Список возвращает `items`, `next_cursor` и `has_more`. Дорогой полный count не обязателен. Ошибки имеют `{error: {code, message, fields?, request_id}}`; неизвестный UUID фильма → 404, неверный cursor → 400, неверные параметры → 422, недоступная БД → 503. В ответах нет traceback или ключей поставщика.

MovieSummary содержит `id`, `title`, `original_title`, `year`, `runtime_minutes`, `poster`, `genres`. MovieDetail добавляет synopsis, backdrop, release details, provenance и ссылки на credits. Media DTO содержит URL, alt/description и source. Детальная схема публикуется в OpenAPI и используется для generated TS client.

## 6. Поиск и покрытие каталога

Приоритет поиска: точное нормализованное название → префикс → вхождение → similarity. Альтернативные названия участвуют в поиске, но один фильм появляется в выдаче один раз. Для коротких запросов используются точные/префиксные совпадения; fuzzy fallback включается для более длинных строк и проверяется на fixtures.

Нормализация включает регистр, пробелы, Unicode и пунктуацию. Для диакритики и названий на разных языках хранится отдельный поисковый ключ/alias. Система не обещает произвольную транслитерацию без данных. Год распознаётся в явно поддержанном формате `Title (YYYY)`; другие числа могут быть частью названия.

**Покрытие:** первая реализация ищет по собственному импортированному каталогу. В UI это объясняется честно. Расширение каталога выполняется импортом выбранных provider feeds/IDs. Поиск по всей внешней базе с on-demand ingest — отдельное последующее расширение, а не скрытый синхронный запрос к поставщику на каждом вводимом символе.

## 8. Измеримые критерии UX и скорости

Следующие значения — цели проекта, а не уже полученные результаты:

- Основные интерактивные элементы рассчитаны на удобное нажатие; ориентир 44 CSS px для touch-сценариев.
- При переходе Back возвращаются URL-state, количество загруженных карточек и scroll; после hard reload восстанавливаются как минимум запрос/фильтры/сортировка из URL.
- Поиск отправляется после примерно 200–300ms паузы; старые запросы отменяются или их ответы игнорируются.
- Во время запроса видна обратная связь, уже загруженные карточки не исчезают без причины; размер постеров зарезервирован до загрузки.
- На 10k fixtures: цель search API p95 ≤ 500ms и detail p95 ≤ 300ms при 10 одновременных клиентах. Измерить после warm-up на 200 read-only запросах к собственной БД без live-provider; указать машину и конфигурацию.
- В production build на выбранном mobile-web профиле: LCP ≤ 2.5s, CLS ≤ 0.1 как лабораторные цели. Отзывчивость проверять сценариями и browser trace; реальные полевые метрики становятся доступны после запуска.
- Проверить widths 360/390/768/1440px, Chrome/Safari и хотя бы один реальный телефон. Результаты симулятора не выдаются за проверку на устройстве.

## 9. Проверки и данные для них

Обязательные fixtures: одинаковые названия разных лет, заголовок с числом, aliases на разных языках, диакритика, объявленный будущий релиз, неизвестная дата/длительность, отсутствующий постер, длинное название, повторный внешний ID, несколько ролей одного человека.

Тесты проверяют поведение: миграции на чистой PostgreSQL; idempotent import; rollback при ошибке; search relevance; сочетания фильтров; cursors; 404/422; DTO/OpenAPI; основные web-переходы и восстановление состояния. Они выполняются с fixtures без сетевого доступа к поставщику. Live-provider smoke test запускается отдельно при наличии разрешённого ключа.

Проверки UI включают loading/empty/error, keyboard navigation и реальный размер экрана. Проверки сборки — отдельный шаг: работа dev server не доказывает готовность production build.
